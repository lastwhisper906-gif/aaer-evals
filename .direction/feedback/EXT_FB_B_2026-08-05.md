# EXTERNAL FEEDBACK DOCUMENT B (received 2026-08-05, saved verbatim)

총평
상당히 잘 만든 개인 연구 레포입니다. 특히 사전등록, 결과별 한계 병기, 해시 고정 의존성, 공개 검증 명령, AI·사람 기여도 공개는 보통 개인 프로젝트보다 훨씬 강합니다.
다만 지금 상태는 감사 문서가 매우 정교한 탐색적 실험에 가깝고, 제3자가 신뢰할 수 있는 독립 벤치마크라고 부르기에는 몇 가지 핵심 문제가 있습니다.

가장 먼저 고칠 4개

1. 교란 실험이 모델에 블라인드되지 않았습니다
build_payload()는 교란된 입력에 다음 정보를 넣습니다.
"variant": "perturbed"
"perturb_factor_recorded_scoring_side_only": null
그리고 runner.py는 _로 시작하는 필드만 제거한 뒤 나머지 payload를 전부 모델에게 보냅니다. 즉, 모델이 "지금 익명화·교란 실험을 받고 있다"는 사실을 알 수 있습니다.
이 상태에서 원본과 교란 점수 차이를 전적으로 '회사 기억 제거 효과'로 해석하기 어렵습니다. 모델이 실험 조건을 눈치채고 더 보수적이거나 다르게 답할 수 있기 때문입니다.
다음처럼 완전히 분리해야 합니다.
payload_for_model = {
    "case": public_case_fields,
    "financial_series_point_in_time": series,
    "filing_chronology": chronology,
}

run_metadata = {
    "variant": "perturbed",
    "perturb_factor": k,
}
variant, 교란 계수, 교란 여부를 암시하는 이름은 모델 payload에 절대 들어가지 않도록 테스트까지 추가하는 것이 최우선입니다.

2. 컷오프 보장에 대한 문서와 실제 코드가 다릅니다
METHOD.md는 사후 데이터가 감지되면 로드가 예외로 즉시 실패한다고 설명합니다.
하지만 실제 벌크 로더는:
if filed <= cutoff:
    rows.append(...)
처럼 사후 행을 제외하고 계속 실행합니다. EDGAR chronology도 같은 방식입니다. 로그의 "facts_after_cutoff"에는 오히려 보존된 len(rows)가 기록되어 이름도 반대로 되어 있습니다.
필터 방식 자체가 반드시 나쁜 것은 아닙니다. SEC의 companyfacts 파일에는 컷오프 이후 자료가 함께 있는 것이 자연스럽기 때문입니다. 문제는 코드보다 강한 보장을 문서가 주장한다는 점입니다.
권장 구조는 다음과 같습니다.
원시 SEC 파일에 사후 데이터가 존재하는 것: 허용
payload 조립 과정에서 사후 데이터를 제거하는 것: 명시적 필터
완성 payload에 사후 데이터가 단 한 건이라도 존재하는 것: 즉시 실패
로그 이름:
facts_total
facts_retained_pre_cutoff
facts_dropped_post_cutoff
그리고 METHOD 문구도 "원시 파일을 읽는 순간 실패"가 아니라 "완성 payload의 컷오프 위반은 fail-closed"로 바꾸는 것이 정확합니다.

3. 동일 모델 계열이 연구 거의 전체를 담당합니다
레포 자체가 다음을 솔직히 공개하고 있습니다.
코드 작성은 사실상 전부 Claude
연구 설계 초안도 Claude
채점 1차도 Claude 계열
논문·README 문구도 Claude
최종 사람 검토에서 기록된 override는 0건
아직 일부 문서는 "pending human audit" 상태
정직하게 공개한 점은 좋지만, 외부 독자는 사람이 독립적으로 검증한 것인지, 매우 정교하게 AI 결과를 승인한 것인지 구분하기 어렵습니다.
최소한 다음 검증이 필요합니다.
무작위 20~30% 사례를 외부 회계 지식 보유자가 블라인드 재채점
기존 점수와 독립 채점자의 Cohen's κ 또는 weighted κ 보고
회사명·처리군 여부·모델 점수를 숨긴 채 근거 인용만 평가
분쟁 사례는 모델이 아니라 인간 2인 합의로 확정
"0 overrides" 대신 agreement matrix와 disagreement 사례 공개
다른 Claude 모델을 한 번 더 돌리는 교차모델 실험은 모델 민감도 측정에는 유용하지만, 독립 인간 감사의 대체재는 아닙니다. 현재 교차모델 계획도 Claude 계열 내부 비교로 한정돼 있습니다.

4. 진짜 핵심은 더 큰 prospective holdout입니다
현재 결과는 작습니다.
wave 1: 처리군 8
wave 2: 처리군 9
post-cutoff holdout: 3
wave 2 처리군 9개 중 모델이 실제 사건을 알고 있던 사례: 8개
따라서 다음 버전의 가장 큰 가치는 문서나 테스트 추가가 아니라 사건 발생 전에 고정된 예측을 축적하는 것입니다.
권장 설계:
매월 전체 미국 상장사 중 사전 규칙으로 유니버스 동결
해당 월의 payload·점수·프롬프트 해시를 공개 timestamp로 봉인
이후 12~24개월 동안 Item 4.02, AAER, SEC complaint 발생 여부 추적
평가 시점까지 threshold 변경 금지
처리군이 생긴 후 대조군을 고르는 대신, 처음부터 전체 유니버스 점수 보존
사건 발생 전 점수만 사용
이렇게 해야 작은 선별 case-control 실험에서 벗어나 실제 스크리닝 성능, PPV, workload, false-alert 비용을 계산할 수 있습니다.

코드 수준에서 바로 고칠 것

5. "확률"과 "서열 점수"가 충돌합니다
프롬프트와 JSON Schema는 모델에게 0~100의 misstatement_probability를 요구합니다.
그런데 결과 문서는 이 수치가 확률이 아니라 ordinal score라고 강조합니다.
둘 중 하나로 통일해야 합니다.
확률로 유지: 별도 calibration set을 만들고 isotonic 또는 Platt calibration 적용
서열 점수로 전환: 이름을 misstatement_risk_score로 바꾸고 ECE·Brier를 주지표에서 제거
현재처럼 "확률을 출력하라"고 시킨 뒤 "사실 확률이 아니다"라고 해석하는 것은 독자에게 혼란을 줍니다.

6. JSON Schema가 설명만큼 강제적이지 않습니다
현재 schema의 checklist는 minItems: 1입니다. 따라서 CL1~CL8 중 하나만 답해도 schema를 통과할 수 있습니다. top_signals도 설명에는 checklist ID만 허용한다고 쓰였지만 실제 enum이나 참조 강제는 없습니다. 위험 등급과 점수 간 정합성도 설명으로만 존재합니다.
다음을 강제하는 편이 좋습니다.
checklist 정확히 8개
item_id는 CL1~CL8 enum
item ID 중복 금지
모든 ID가 정확히 한 번 등장
top_signals도 CL1~CL8 enum
misstatement_probability >= 70 → elevated
misstatement_probability < 40 → elevated 불가
accession 번호 형식 검증
날짜 형식 실제 검증
현재 validator는 Draft7Validator(schema)만 사용하므로 date, date-time 같은 format은 실질적으로 검사되지 않습니다. format_checker=jsonschema.FormatChecker()를 넣어야 합니다.

7. fingerprint 없는 기존 결과를 자동 신뢰합니다
runner.py는 기존 출력이 schema만 통과하고 fingerprint가 없으면 다음처럼 건너뜁니다.
legacy output — fingerprint 없음, 재실행 안 함
이 경우 프롬프트, schema, pipeline 코드가 바뀌어도 오래된 결과가 계속 사용될 수 있습니다.
기본 동작은 다음이어야 합니다.
fingerprint 없음 → stale 처리 후 재실행
예전 결과를 그대로 쓸 때만 --accept-legacy-output
legacy 파일에는 별도 provenance manifest 생성
발표 숫자는 fingerprint가 존재하는 출력만 허용

재현성과 CI 개선

8. verify-public은 "전체 재현"이 아니라 "커밋 산출물 재계산"입니다
현재 공개 검증은 매우 유용하지만, 실제로는 이미 커밋된 모델 출력과 중간 산출물에서 숫자를 다시 계산하는 구조입니다. 모델 실행과 원시 데이터 payload 생성은 포함하지 않습니다. 레포도 뒷부분에서는 이를 인정하고 있습니다.
표현을 다음처럼 구분하면 더 정확합니다.
verify-claims: 커밋 산출물로 발표 숫자 재계산
verify-pipeline: 공개 fixture에서 payload 생성부터 테스트
reproduce-corpus: 전체 원시 데이터 재구축
rerun-evaluatee: 모델 호출까지 포함하는 비결정적 재실행
그리고 3~5개 synthetic 또는 라이선스상 배포 가능한 실제 사례를 포함한 작은 fixture corpus를 제공하면 제3자가 cutoff → payload → scoring 전 경로를 검증할 수 있습니다.

9. CI 공급망과 품질 검사를 보강할 수 있습니다
현재 CI는 Python 3.11~3.13을 실행하지만 3.11과 3.13 실패를 허용합니다. 또한 GitHub Actions는 actions/checkout@v4, setup-python@v5처럼 태그로만 고정되어 있습니다.
추천:

Actions를 전체 commit SHA로 고정
workflow에 permissions: contents: read

pip-audit
Dependabot

현재 297개 테스트는 강점이지만, 테스트 개수와 정적 타입·보안·coverage는 서로 다른 품질 축입니다.

통계와 문서에서의 개선

10. 통계는 더 단순하고 표준적으로 만들 수 있습니다
현재 자체 구현된 permutation, bootstrap, Clopper–Pearson 계산이 많습니다.
권장 사항:
Monte Carlo permutation p-value에는 Monte Carlo 표준오차 또는 interval 병기
가능한 작은 표본은 exact permutation 사용
AUC CI는 bootstrap 방식과 seed를 표에 직접 표시
여러 탐색 분석은 primary·secondary·exploratory로 기계적으로 구분
ordinal score에는 ECE보다 rank metric 중심
실제 희귀 사건에서는 ROC-AUC보다 PR-AUC와 PPV가 중요
threshold별 alerts per 1,000 firms 보고
post-hoc 결합 규칙은 다음 prospective cycle에서만 평가

11. 문서가 너무 복잡합니다
D, Q, RP, E, R, H 같은 식별자가 너무 많아 처음 보는 사람은 결과보다 내부 거버넌스 체계를 먼저 해독해야 합니다. README도 첫 화면부터 매우 많은 수치와 한계가 등장합니다.
추천 구조는 단순합니다.
README.md: 질문·결론·가장 큰 한계·재현 명령
METHOD.md: 실제 파이프라인
RESULTS.md: primary 결과만
CLAIMS.json: 수치, source artifact, limitation, status
audit/: D/Q/RP 전체 기록
현재 GitHub Issues #1~#3을 논문 발행 표면으로 사용하면서 계속 open 상태로 둔 것도 일반적인 issue tracker 사용과 충돌합니다. release 또는 GitHub Pages를 발행 표면으로 쓰고, issue는 질문·버그·재현 실패용으로 비워두는 편이 낫습니다.
