# Weakness, read on the night of 2026-10-21: the accounting analyst names adjustments it cannot write

The improvement loop's first weakness file (`docs/improve_loop.md`, step 1),
written by hand in this session, not by a pass of `make improve`.

## Evidence

Over the 29 runs published before tonight, `adjustments` holds 0 to 2 items
per run and 0 in 19 of them (`.venv/bin/python -m src.improve.mine --runs runs
--table`, column *adjustments*). The gate did not drop them: across all runs
the dropped items under `adjustments` number 4 (CIEN 1, ESE 1, LFUS 2). The
analyst did not write them.

The transcripts, kept on disk since 2026-10-21, say why, in the analyst's own
closing words:

- `runs/OMCL/.0000926326-26-000022.logs/accounting-analyst.1.transcript.jsonl`:
  "No adjustments were written. Each adjustment the findings call for —
  removing the tariff refund, the cash from receivables sales, the lower
  bad-debt charge and the advance-billing lift — needs a calculator field
  holding the amount, and none exists. As a result, the quality-adjusted free
  cash flow still includes the refund and the advance-billing lift, so it
  overstates the run rate."
- `runs/NTAP/.0001193125-26-380207.logs/accounting-analyst.1.transcript.jsonl`:
  "The analysis lists 37 anomalies but makes no adjustments to free cash flow
  or earnings. The calculator has no field for the amounts involved:
  receivables sales, supplier finance, guarantees, the acquisition's
  contingent payment and the extra week."

Both runs list the anomalies (31 and 37) and both leave `adjustments` empty,
so the one bridge between the accounting and financial frames
(`free_cash_flow_quality_adjusted`, `CLAUDE.md`) carries nothing on them.

## Root cause

The adjustment rule (`.claude/agents/accounting-analyst.md`, *Adjustments*;
`src/calculator.adjustment_amount`): an adjustment names a
`calculator_filings_only.json` field under `terms.` or `earnings_versus_cash.`
whose whole value, in USD, is the amount. The amounts the analysts want to
move are figures the filing prints in a note or the release and that
companyfacts does not tag as a standard element for these filers: cash from
receivables sold (`proceeds_from_sale_of_receivables` is a term, missing for
both), a tariff refund, a bad-debt charge, a change in advance billing, a
supplier-finance balance's change, a guarantee, a contingent payment, an
extra week's revenue. The rule is right that an agent must not type the
number; the field set is what is short.

## Component responsible

`src/calculator.py`'s term list and `src/fetch_companyfacts.py`'s tags (which
amounts become fields), not the prompt and not the gate. A prompt change
cannot produce a field.

## Remedies a pass would propose, each with its judge

1. **More terms from companyfacts where the filer tags them**: the change in
   contract liabilities (both balances are already terms; the change is one
   `measure`), the change in the supplier-finance obligation (same), the
   bad-debt expense (`ProvisionForDoubtfulAccounts`), the allowance's change
   (both balances held). Judge: hand computations from one company's
   companyfacts in `tests/test_calculator.py`. Cheap; covers OMCL's bad-debt
   and advance-billing items and NTAP's supplier finance.
2. **A verbatim-quoted amount as an adjustment's source**, Python reading the
   number out of a quote the gate verifies against the report, the way a
   `quote` is verified today — the amount never typed by the analyst, only
   quoted. Judge: the gate's tests over planted quotes with and without a
   figure. This changes a rule `CLAUDE.md` states ("every number an agent
   writes comes from calculator.json or companyfacts"), so it is the owner's
   row, not a pass's edit.
3. **The notes reader tagging amounts**: the notes-text reader already quotes
   the sentence; a reader item carrying the figure as a field Python can
   verify would make it citable. Judge: the quote gate's tests. The same
   rule question as 2.

Remedy 1 is a calculator change under the two lenses; 2 and 3 are in
`docs/needs_judgment.md`.
