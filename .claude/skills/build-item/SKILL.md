# Build one task-list item

The item is `$ARGUMENTS` — its title from `docs/next_cycle_tasks.md`.

## 1. Read the item before touching anything

Find its line. Read its four fields: **builds**, **judge**, **expected value
from**, **PR**.

Then ask the only question that stops the build before it starts:

> Does the expected value come from the code under test?

If the judge's expected numbers would be produced by running the thing being
built — a fixture regenerated by the parser, an acceptance file the builder
writes from its own output, a test that asserts what the function returned —
**stop**. Mark the item `needs judgment` with one line naming what the expected
value would have to come from instead, and do not build it. This has already
happened once: ten of twelve items certified themselves, the reproduce lens
passed on the circular evidence, and only the refute lens caught it.

An item with no judge at all is also `needs judgment`. Never launch one.

## 2. Implement in a worktree

One worktree per item, one branch per item, one pull request per item.

Build the expected values **first**, from the source: the filing itself, the
companyfacts JSON, or a hand computation written into the test so a reader can
follow the arithmetic. Then write the code that has to match them.

Never touch `runs/`, `rules/` or `events/`. Never change a test expectation to
make a test pass.

## 3. `make check`

Red means there is no next step. Not "red but unrelated", not "red on a
pre-existing failure" — fix it or stop.

Run it on the pinned interpreter, Python 3.12. A result from another interpreter
is not worth producing. Never put a pipe between the test run and anything that
depends on it passing; a pipeline's exit status is the last command's, and a red
suite has been committed that way before.

## 4. Call `refute-check`

Hand it the diff and the item's four fields.

- `fail` → fix it and go back to step 3.
- `needs judgment` → mark the item, stop, leave one line. Do not decide it
  yourself and do not open a pull request that carries the question.
- `pass` → continue.

## 5. Open the pull request with auto-merge on

```sh
gh pr create --fill
gh pr merge --auto --squash
```

Auto-merge goes on the moment the pull request opens. A pull request waiting for
a click is the bottleneck the rules forbid, not a safety measure — a step is not
finished until the merge is automatic.

Write the pull request number into the item's `PR` field in
`docs/next_cycle_tasks.md` and commit that line.

## 6. Leave the record

Append this item's mistakes to `lessons.md`, one line each, no judgment. If it
produced none, append nothing.
